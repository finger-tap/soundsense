# 「闻声」输入源选择 · 技术调研与方案

> 调研对象：Mac 端（含跨设备）能否让用户选择声音输入源
> 调研日期：2026-09-30
> 当前部署目标：macOS 12.0 / iOS 15.0 / watchOS 9.0

---

## 一、先说结论

你的设想**对了一半**。

**对的部分**：macOS 确实有能力枚举并切换音频输入源，这是 CoreAudio 的原生能力，不需要装任何驱动或系统组件。

**需要纠正的部分**：

### 1.「听筒」不是输入源

听筒（receiver）是**输出**设备。iPhone 上真正贴近听筒位置的那颗麦克风，属于「内建麦克风」的一个数据源（data source），不是一个独立的选项。

分贝计只关心**输入**方向，所以输入源列表里不应该出现「听筒」。如果要做的是输出路由（测的时候用哪个喇叭放声音），那是另一件事，和测量无关。

### 2.「电脑的 / 手机的 / 手表的」不是三个平行选项

它们在系统层面是三种完全不同的东西，可行性天差地别：

| 目标 | 系统层面是什么 | 可行性 | 需要做什么 |
|---|---|---|---|
| 电脑的麦克风 | 本机 CoreAudio 设备 | ✅ 完整可控 | 写代码枚举 + 切换 |
| 手机的麦克风 | 连续互通相机（Continuity Camera）注册的系统输入设备 | ✅ 系统原生，零成本 | 只需**列出来** + 引导用户开启 |
| 手表的麦克风 | 不存在这条路 | ❌ 无官方 API | 只能换思路（见方案 C） |

**关于手表这条**：Apple 从来没有提供「把 Apple Watch 当作另一台设备的麦克风」的 API。WatchConnectivity 只能与**配对的 iPhone** 通信，不能直接和 Mac 通信；而且它也不是音频流通道。

## 二、Mac 上实际能枚举到哪些输入源

把 `kAudioHardwarePropertyDevices` 拉全量，再按「输入通道数 > 0」过滤，实际会看到这些类别：

| 类型 | 典型例子 | transport type | 对分贝计是否可用 |
|---|---|---|---|
| 内建麦克风 | MacBook Pro 麦克风 | `BuiltIn` | ✅ 主力，默认 +93 dB |
| USB / 雷电麦克风 | Blue Yeti、音频接口 | `USB` / `Thunderbolt` | ✅ 可用，通常 +85 dB 左右 |
| 蓝牙耳机麦克风 | AirPods | `Bluetooth` / `BluetoothLE` | ⚠️ **不建议**，见下方说明 |
| iPhone 麦克风 | 「iPhone 麦克风（连续互通）」 | `ContinuityCapture` (`'ccap'`) | ✅ 系统级支持，音质不错 |
| 虚拟声卡 | BlackHole、Loopback | `Virtual` | ⚠️ 测的是系统内部声音，不是环境噪音 |
| 聚合设备 | 多设备聚合 | `Aggregate` | ⚠️ 时钟同步复杂，不建议 |

### ⚠️ 蓝牙耳机麦克风是个坑，建议直接排除

这不是偏见，是物理限制：

1. **采样率被砍**。AirPods 做输入时走 HFP/HSP 协议，采样率降到 16 kHz 甚至 8 kHz。而当前算法是 4096 点 FFT，48 kHz 下有效分析频段约 20 Hz–20 kHz；一旦掉到 16 kHz，最高只能看到 8 kHz。A 计权在 8 kHz 以上仍有能量贡献（虽然衰减，但不可忽略），截断会系统性低估读数。
2. **AGC 是致命的**。HFP 链路通常带自动增益控制。分贝计测的是**绝对声压级**，AGC 一介入，输入电平就跟真实声压脱钩了 —— 这正是项目 README 里特意强调「关闭 AGC/高通」的原因。

**建议**：在设备列表里把蓝牙输入源标注为「不推荐」，或者干脆折叠进「高级」分组，别让用户误选。

## 三、三个方案

### 方案 A：Mac 本机输入源选择 ⭐ 推荐先做

**能做什么**：列出本机所有可用输入设备，用户在设置里选一个，App 内部切换，**不改系统默认输入设备**。

**关键 API 链**（全部是 CoreAudio 公开 API，无需权限）：

```swift
// 1. 枚举所有设备
var addr = AudioObjectPropertyAddress(
    mSelector: kAudioHardwarePropertyDevices,
    mScope: kAudioObjectPropertyScopeGlobal,
    mElement: kAudioObjectPropertyElementMain)
// AudioObjectGetPropertyDataSize → AudioObjectGetPropertyData → [AudioDeviceID]

// 2. 过滤出有输入通道的（用 kAudioDevicePropertyStreamConfiguration，
//    看 mScope = kAudioDevicePropertyScopeInput 下的 buffer 数量）

// 3. 取元数据
//    kAudioDevicePropertyDeviceNameCFString  → 显示名
//    kAudioDevicePropertyDeviceUID           → 稳定标识（用于存校准值）
//    kAudioDevicePropertyTransportType       → 分类（内置/USB/蓝牙/连续互通/虚拟）

// 4. 切换（★ 必须在 engine 停止状态下做）
try engine.inputNode.auAudioUnit.setDeviceID(newDeviceID)
```

**关于 `AUAudioUnit.setDeviceID(_:)`**：这是官方的现代写法（仅 macOS），比老的 `AudioUnitSetProperty(kAudioOutputUnitProperty_CurrentDevice)` 干净。后者是社区用了一万年的方案，Apple 的 DTS 曾在邮件列表里确认「AVAudioEngine 默认只能用系统默认输入输出设备」，但底层 AudioUnit 这条路实测可行，两代方案都在生产环境用着。

**注意**：`AUAudioUnit.setDeviceID` 会把输入输出**一起**切到同一个设备。如果只想换输入、保留原输出，需要单独调用 `outputNode` 的 deviceID 设置。对分贝计来说只录不放，直接设输入即可，但要留意这一点。

**工作量**：1–2 天（含 UI）。

---

### 方案 B：iPhone 麦克风 —— 零成本，只需「列出来 + 引导」

这是本次调研最有价值的发现：

**macOS 13 (Ventura) 起，iPhone 的麦克风会作为标准 CoreAudio 输入设备出现在系统里**，走的是连续互通相机（Continuity Camera）能力。它和 USB 麦克风一样出现在设备列表中，第三方 App 直接枚举就能选到。

也就是说 —— **你要的「选手机的麦克风」，系统已经实现了，我们不需要写任何跨设备传输代码**。

我们需要做的只有三件事：

1. **检测**：枚举时判断 transport type 是否为 `kAudioDeviceTransportTypeContinuityCapture`
   （该常量声明为 macOS 13.0+，部署目标是 12.0，需要 `@available` 守卫 + 硬编码四字符码 `'ccap'` 兜底）
2. **展示**：在设备列表里给它一个单独的图标/分组，标注「iPhone 麦克风」
3. **引导**：如果没检测到，显示一张引导卡片，告诉用户怎么开：
   - Mac 和 iPhone 登录同一 Apple ID，开启双重认证
   - 两台设备都打开 Wi-Fi 和蓝牙，距离 10 米内
   - iPhone：设置 → 通用 → AirPlay 与连续互通 → 打开「连续互通相机」
   - 首次使用建议先用 USB 线连一次，建立信任关系
   - **iPhone 需要横放、保持稳定、屏幕熄灭**才作为 Mac 麦克风工作

最后一条对分贝计其实是加分项：手机放着不动测环境噪音，正是标准使用姿势。

**限制**（说人话）：
- 依赖网络链路（Wi-Fi/蓝牙），有压缩和延迟。测稳态噪音没问题，测瞬时脉冲（比如敲墙那一下）时间精度不可信
- 无线链路会丢包重传，极端情况下有卡顿
- 需要 macOS 13+，部署目标 12.0 的机器用不了（要升版本或做降级提示）

### 方案 C：Apple Watch —— 不做「输入源」，改做「远程测量端」

**直说：技术上没有路**。Apple 不提供任何 API 让 Mac/iPhone 把 Apple Watch 当麦克风用。

但**需求本身是可以满足的**，只要换个架构：

> **分贝值是标量，不是音频流。**

手表本地采集、本地算分贝，然后把**数值**传出去 —— 这条路项目里已经在跑了：`WatchSyncManager` 就是通过 `WCSession.didReceiveMessageData` 收手表传来的 `SourceTestResult`。

对比一下两条路：

| 路径 | 数据量 | 延迟 | 耗电 | 对测量的价值 |
|---|---|---|---|---|
| 传分贝数值 | 每帧几十字节 | 低 | 低 | ✅ 完整（数值就是结果） |
| 传音频流 | 48kHz 单声道约 1.5 Mbps | 数百 ms 起 | 高 | ❌ 无增益，还得在接收端重算 |

而且 WatchConnectivity 不是为流式音频设计的 —— 实测做法是把 PCM 聚合成 1.5 秒的块再发（社区项目 Friend / anarlog 的做法），前台用 `sendMessage`、后台退化成 `transferUserInfo`。这个延迟做环境噪音长期监测够用，做声源定位的走位时序就不够了。

**建议**：把手表定位成「分布在不同房间的第二个测量点」，传数值，不传音频。要走远一点的话，可以把 `SourceTestResult` 同步扩展成实时测量数据同步，让 Mac 端能同时看到「本机麦克风」和「手表麦克风」两条曲线 —— 这才是「选手表的声音」这个需求的正确解法。

## 四、三个必须处理的坑

### 坑 1：校准偏移量必须跟着设备走 ⚠️ 最容易被忽略

**现在的实现**：`calibrationOffset` 是单个 `@AppStorage` 值（Mac 默认 93，iOS 默认 93）。

**问题**：不同麦克风的灵敏度差异可以到 20 dB 以上。Mac 内建麦克风 +93、外接麦克风 +85 只是粗分类，iPhone 麦克风又是完全不同的值。**一旦切了源但不换校准值，读数直接就是错的** —— 而且错得很隐蔽，用户根本看不出来。

这比切换功能本身更重要。功能做出来但读数不准，比没有这个功能还糟。

**方案**：
1. 把校准值改成按设备 UID 索引的字典：`[String: Double]`，key 用 `kAudioDevicePropertyDeviceUID`
2. 切换设备时自动载入该设备上次用的偏移量
3. 新设备首次出现时，按 transport type 给一个预设初值（内置 +93 / USB +85 / 连续互通 +93），并在 UI 上提示「该设备尚未校准」
4. 设置页的预设按钮改成「为当前设备恢复默认」

**参考默认值**（需实测微调，只能当起点）：

| 设备类型 | 建议初值 |
|---|---|
| Mac 内建麦克风 | +93 dB |
| USB / 外接麦克风 | +85 dB |
| iPhone 麦克风（连续互通） | +93 dB（待实测） |
| 蓝牙输入 | 不给值，直接标注不推荐 |

### 坑 2：切换设备时的格式重配顺序不能错

已知崩溃模式（Apple 开发者论坛 + 多个真实崩溃报告）：

```
required condition is false: format.sampleRate == hwFormat.sampleRate
IsFormatSampleRateAndChannelCountValid(format)
AVAudioIONodeImpl::SetOutputFormat
```

根因：切设备后 `inputNode` 的 format **不会自动更新**，仍持有旧设备的采样率/通道数，重装 tap 时就崩了。

**正确顺序**（一步都不能少）：

```swift
engine.inputNode.removeTap(onBus: 0)   // 1. 先摘 tap
engine.stop()                          // 2. 停引擎
try engine.inputNode.auAudioUnit.setDeviceID(id)  // 3. 换设备
// 4. 重新读 format —— 注意是 inputFormat，不是 outputFormat
//    切设备后这两个值会不一致，用 outputFormat 会拿到 0 通道
let fmt = engine.inputNode.inputFormat(forBus: 0)
// 5. 用新 format 重装 tap（当前 AudioMeterEngine 里 format 合法性校验已有，需要复用）
// 6. worker.updateSampleRate(fmt.sampleRate) —— 必须！否则 A 计权频率映射全错
engine.start()
```

**特别注意第 6 步**：`MeterWorker` 里 `DBMeter` 是按采样率构建的。48 kHz 内建麦克风切到 44.1 kHz 的 USB 麦克风，如果不更新采样率，A 计权的频率轴就整体偏了约 8.8%，读数会系统性出错。

对应现有代码：`AudioMeterEngine.installTapIfNeeded()` 里已经有 `worker?.updateSampleRate(sampleRate)`，切换流程要确保走同一条路径。

### 坑 3：macOS 26 Tahoe 的已知音频 bug

- macOS 26.0.0 / 26.0.1：**输入和输出使用不同设备时**，某些音频捕获会静音（26.1 修复）
- macOS 27 Golden Gate 又修了一批 aggregate device 相关的 CPU 占用和挂起问题

「输入用 iPhone 麦克风、输出用内建扬声器」恰好就是触发场景。建议：
- 在切换后做一次「是否有实际采样数据」的自检
- 或在 Info.plist / 设置页注明最低建议版本

## 五、顺带说一下 iOS 侧（成本很低，建议一起做）

讽刺的是，**iOS 上这个功能反而是官方 API 最完善的**，`AVAudioSession` 原生支持：

```swift
// 列出所有可用输入
session.availableInputs   // [AVAudioSessionPortDescription]
// 切换
try session.setPreferredInput(port)
// 内建麦克风还能选物理位置（底部 / 正面 / 背面）
port.dataSources          // [AVAudioSessionDataSourceDescription]
try port.setPreferredDataSource(ds)
```

**对分贝计的价值**：iPhone 的「底部麦克风 / 正面麦克风 / 背面麦克风」指向性不同。测楼上噪音时，选正面（屏幕侧）麦克风指向天花板，比底部麦克风的信噪比明显更好。这个功能对现有的「声源定位套件」是直接增强。

**两个注意点**：
1. `setCategory(_:options:)` 的 options 会影响可用输入源。当前 iOS 用了 `[.allowBluetooth, .defaultToSpeaker]` —— `.allowBluetooth` 会让 AirPods 进入可选输入列表（也是 16 kHz + AGC 的坑）
2. 切换输入会触发 `AVAudioSession.routeChangeNotification`，需要重新配置 engine

## 六、全版本兼容：矩阵与降级策略

**核心原则：探测能力，而不是判断版本。**

不写 `if #available(macOS 13)` 来决定「能不能用 iPhone 麦克风」—— 而是：枚举到连续互通设备 = 能用，枚举不到 = 列表里就不出现这一项。版本号判断是脆弱的（系统行为会变、文档会滞后），能力探测是稳的。这是让软件在所有版本上都可用的正确架构。

### 6.1 能力兼容矩阵

| 能力 | 依赖 | 最低系统版本 | 低于该版本的行为 |
|---|---|---|---|
| 本机输入源枚举 | CoreAudio HAL | macOS 10.11（老 API） | 不适用，全版本可用 |
| 输入源切换 `setDeviceID` | `AUAudioUnit` | macOS 10.11 | 不适用，全版本可用 |
| 设备插拔 / 默认变更监听 | `AudioObjectAddPropertyListenerBlock` | macOS 10.11 | 不适用，全版本可用 |
| 校准值按设备存 | 纯 App 逻辑 | 无系统依赖 | 全版本可用 |
| iPhone 麦克风（连续互通） | 系统级 Continuity Camera | macOS 13.0 **且** iOS 16.0 | 设备不出现 → 自动隐藏 + 显示引导卡片 |
| 识别连续互通设备的常量 | `kAudioDeviceTransportTypeContinuityCapture` 声明于 macOS 13.0 SDK | — | **不用系统常量**，硬编码四字符码 `'ccap'`，编译期全版本兼容 |

### 6.2 版本间连接矩阵（Mac × iPhone）

| Mac 系统 | iOS 16+ | iOS 15 及以下 |
|---|---|---|
| macOS 26 / 27 | ✅ iPhone 麦克风可用 | ❌ 系统边界（iOS 16 起支持） |
| macOS 13 – 15 | ✅ 可用 | ❌ 同上 |
| macOS 12（当前部署目标） | ❌ 系统边界（连续互通需 macOS 13+） | ❌ 同上 |

**注意**：「iPhone 麦克风不可用」≠「软件不可用」。低版本系统上本机测量照常工作，只是设备列表里没有 iPhone 那一项。软件的核心能力（本机麦克风测量）在 macOS 11 上就完整可用。

### 6.3 降级策略（四层）

1. **功能探测层**：枚举到就列，枚举不到就隐藏。全程零版本判断。
2. **引导降级层**：macOS 12 上显示一次「升级到 macOS 13+ 可把 iPhone 当麦克风用」的说明卡片（可关闭、不重复弹）。
3. **bug 规避层**：macOS 26.0.x 上切换输入源后做「是否真的收到采样数据」的自检，失败时提示重启测量（绕过输入输出异设备的系统静音 bug）。
4. **编译兼容层**：所有新版 API 走 `@available` 守卫 + 硬编码常量兜底，保证在 macOS 12 部署目标下编译通过、运行不误触。

### 6.4 一处需要清理的配置

`project.pbxproj` 里项目级 `MACOSX_DEPLOYMENT_TARGET = 11.0`（Debug 651 行 / Release 683 行），macOS App target 覆盖为 `12.0`（841/868 行）。实际产物按 12.0 走，**不算 bug**，但建议统一为 12.0，避免以后看项目级配置误判支持范围。

> 另注：CLI 工具 `LiveMeter`（`Core/Sources/soundsense/main.swift`）用的是 `outputFormat(forBus: 0)`。它不做选源、只在启动时读一次格式，当前没问题；但如果以后 CLI 也要支持选源，切换后必须改读 `inputFormat(forBus: 0)`（见坑 2），先记着。

## 七、建议的落地顺序

| 阶段 | 内容 | 平台 | 成本 | 依赖 |
|---|---|---|---|---|
| 1 | 本机输入源枚举 + 切换 + 按设备存校准值 | macOS | 中 | 无 |
| 2 | iPhone 麦克风检测 + 开启引导卡片 | macOS | 低 | 阶段 1 的枚举层 |
| 3 | 输入源列表 UI（复用组件） | iOS | 低 | 无 |
| 4 | 手表实时测量数值同步（非音频流） | watchOS↔iOS | 中 | 现有 WCSession 通道 |

**建议先做阶段 1**，因为它独立、收益直接，而且暴露出来的「校准值跟设备走」这个问题是三个阶段共同的地基 —— 地基不打好，后面越做越乱。

## 八、一页速览

**能做**：
- ✅ Mac 本机输入源枚举与切换（CoreAudio + `AUAudioUnit.setDeviceID`）
- ✅ Mac 选用 iPhone 麦克风（系统原生连续互通，只需列出 + 引导）
- ✅ iOS 输入源 + 内建麦克风物理位置切换（`AVAudioSession` 官方 API）
- ✅ 手表测量数值同步（不是音频流）

**不能做**：
- ❌ Mac 直接把手表麦克风当输入设备（无 API，任何版本都没有）
- ❌ 「听筒」作为输入源（概念错误，听筒是输出）

**必须配套做**：
- ⚠️ 校准偏移量改为按设备存储，否则切源后读数错误且用户无感知
- ⚠️ 切换时的 format 重配顺序 + 采样率更新
- ⚠️ 蓝牙输入源标注不推荐（16 kHz + AGC，破坏测量精度）
